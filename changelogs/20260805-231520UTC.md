# 2026-08-05 — Remove Dinghy support

## What changed

- `resolver::macos::nameserver` no longer special-cases `192.168.99.x`-shaped addresses; it just returns the configured nameserver.
- `resolver::macos::configured_to_use_dinghy` removed. `contents_has_our_nameserver` no longer skips the nameserver-line check for such addresses.
- `services::dnsmasq::is_dinghy_match` / `resolve_address` removed; `build_domain_args` uses each domain's configured address directly.
- Removed the now-obsolete tests for the above (`test_nameserver_dinghy_passthrough`, `test_configured_to_use_dinghy`, `test_is_dinghy_match`, `resolve_address_passthrough`).

## Why

This code was a non-functional stub carried over from the original Ruby port: it checked whether a configured address looked like a `192.168.99.x` IP, but never actually resolved anything (comments admitted "we don't have dinghy detection"). Digging into upstream Dory's actual implementation showed the stub was also testing the wrong condition — Dory's `Dinghy.match?` checks whether the user wrote the literal placeholder string `dinghy` (via a lenient regex) as `nameserver`/`address`, then shells out to `dinghy ip` to substitute the current Dinghy VM's IP at the point of use. The `192.168.99.x` prefix check in aka never matched that real use case.

Dinghy itself has been unmaintained since Docker Desktop for Mac made its VirtualBox-based Docker host unnecessary, so real detection wasn't implemented — the dead stub was deleted instead. `README.md` documents that a literal `dinghy` value is now used as-is rather than resolved.

Note: `services::proxy::CUSTOM_PROXY_IMAGE` (`codekitchen/dinghy-http-proxy:2.5.10`) is unrelated and untouched — it's just the Docker image used for custom SSL certs, not VM IP detection.
